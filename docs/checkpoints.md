# 막히지 않고 진행하는 방법

[English](en/checkpoints.md) | **한국어** · [전체 과정](../README.ko.md)

한 번에 한 단계만 진행합니다. **명령 입력 → 결과 확인 → 다음** 순서를 유지하세요. 별도 작성·제출 단계는 없습니다. 명령이 저장한 설정과 결과 파일을 그대로 보관합니다.

**처음에는 한 언어의 기본 경로만 따라갑니다.** 과거 검증 보고서나 접힌 복구 절의 명령을 추가 과제로 실행하지 않습니다. 장을 건너뛰었다면 다음 장 첫머리의 **시작 조건**부터 확인하세요.

## 명령과 자리표시자 읽기

| 문서에 보이는 것 | 할 일 |
|---|---|
| `python ...`, `az ...`, `azd ...` | README가 있는 폴더의 터미널에서 한 줄씩 실행합니다. |
| `bash` / `powershell` | 코드 상자의 언어 표시입니다. 이 단어 자체는 입력하지 않습니다. Python 명령은 활성화된 가상 환경에서 두 셸 모두 사용합니다. |
| `실제-...`, `YOUR-...`, `ACTUAL-...`, `<...>` | 바로 앞 단계에서 확인한 **내 값**으로 바꿉니다. 따옴표는 남기고 꺾쇠는 넣지 않습니다. |
| `--label baseline` | 결과 묶음 이름입니다. 첫 실행은 예시 이름을 써도 됩니다. 바꾸면 후속 `evaluate`·`compare` 등의 참조도 모두 바꿉니다. |
| `--output outputs/...json` | 답변을 저장할 새 파일 경로입니다. 실행 뒤 편집기에서 그 파일을 엽니다. |
| JSON/YAML/질문만 있는 상자 | 터미널 명령이 아닙니다. 안내한 파일에 저장하거나 Playground의 질문 입력란에 붙여 넣습니다. |
| `선택`, `대신`, 접힌 복구 절 | 기본 명령에 **추가로 전부 실행하지 않습니다**. 해당 조건일 때만 실행합니다. |

여러 줄이 있는 코드 상자도 **한 줄씩** 실행합니다. 일반 명령은 입력 프롬프트가 돌아온 뒤 결과를 읽고 다음 줄로 갑니다. `serve`처럼 실행한 채 두는 서버만 예외이며, 그 장에서 터미널 A/B를 안내합니다.

`--confirm-create`, `--confirm-cost`, `--confirm-delete`는 각각 생성·과금·삭제 의사를 명시하는 옵션입니다. **이 옵션이 없는 모델 호출도 과금될 수 있습니다.** 설명에서 호출 대상과 비용을 먼저 확인합니다.

## 결과 파일을 읽고 다음 명령에 값 옮기기

편집기의 파일 탐색기에서 출력된 경로를 엽니다. 폴더만 만들어졌거나 마지막 줄에 경로가 표시됐다는 이유로 성공으로 판단하지 않습니다.

| 출력/파일 | 읽는 방법 |
|---|---|
| `.json` | `"이름": 값` 형식입니다. 다음 명령에는 **필드 이름이 아닌 값만** 복사합니다. |
| `.jsonl` | 한 줄이 사례 하나입니다. 6문항 결과라면 실제 6행과 각 행의 오류를 확인합니다. JSON 배열로 바꾸지 않습니다. |
| `.html` | 편집기에서 코드만 읽지 말고 파일을 브라우저로 열어 표와 사례별 결과를 봅니다. |
| `true` / `false` / `null` | 참 / 거짓 / 값 없음입니다. `null` 사용량은 0원이나 호출 없음이 아닙니다. |
| `manifest.json` | 이번 실행의 모델·지침·데이터·설정을 기록합니다. 답변은 해당 응답 파일에서 확인합니다. |
| `result_directory` 또는 저장 경로 | 그 폴더/파일을 엽니다. 응답·평가·소유권 파일은 각각 다른 기록입니다. |

**이름도 종류를 구분합니다.** `prepare-hosted --name hosted`의 `hosted`는 **접두사 뒤의 짧은 이름**입니다. 도구가 전체 서비스 이름을 출력하면 이후 `azd deploy`에는 그 전체 값을 넣습니다. 반면 `prompt-agent create --name`은 내 접두사를 포함한 **전체 agent 이름**을 받습니다. 모든 `--name`에 같은 문자열을 일괄 대입하지 않습니다.

08장 이후의 패키지 경로·준비 폴더·서비스·버전은 [08의 값 복사 표](08-hosted.md#3-기존-프로젝트에-연결하는-독립-폴더)를 보고 **명령 출력에서 다음 명령으로 직접 복사**합니다. `--cwd`는 azd 한 명령의 대상 폴더를 지정할 뿐, 터미널의 현재 위치를 바꾸지 않습니다. 터미널은 계속 README가 있는 폴더에 둡니다.

| 06 원래 Search index | `outputs/learner-notes-ko/06-search.json`의 `configuration.index` |
| 07 전후 평가 | `outputs/baseline/`, `outputs/candidate/`. label을 바꿨다면 그 이름의 폴더 |

파일 존재만으로 완료를 판단하지 않습니다. 각 장의 **완료 확인**과 실제 행 수·오류·판정을 대조합니다. 포털에서만 한 작업까지 모두 로컬에 자동 저장된다고 가정하지 않습니다.

## 다음 날 재개하기

**같은 프로젝트라면 설치·생성부터 다시 하지 않습니다.** 이전 폴더 전체와 `.env`, `.selfstudy/`, `outputs/`를 유지합니다.

1. 편집기에서 기존 실습 폴더를 열고 새 터미널을 엽니다.
2. 본인 OS의 활성화 명령 **하나만** 실행합니다.

macOS / Linux:

```bash
source .venv/bin/activate
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

활성화가 조직 정책으로 막히면 정책을 바꾸지 말고 `python` 대신 `.\.venv\Scripts\python.exe`를 사용합니다.

3. 00장의 `configure`를 마친 환경에서 다음을 실행합니다.

```bash
python scripts/workshop.py doctor
python scripts/selfstudy.py values
```

`PASS`와 **내 프로젝트·접두사·모델**을 확인합니다. `values`와 `status`는 저장된 설정을 읽을 뿐 Azure 자원의 현재 존재/상태를 검사하지 않습니다. `먼저 Lab 00의 configure`가 나오면 [00의 설정 단계](00-setup.md#8-실제-값으로-설정-자동-수집)로 돌아갑니다. 로그인 만료는 00의 정상 `az login`/`azd auth login`으로 해결합니다.

4. 위 표에서 해당 장의 결과를 열고 **완료 확인**과 대조한 뒤, 아직 수행하지 않은 다음 단계부터 이어갑니다. 이미 받은 답변을 확인하려는 목적이라면 파일을 열면 되며 모델을 다시 호출할 필요가 없습니다.

### 두 터미널을 사용하는 장

05·08·10장의 **터미널 A**는 서버를 실행한 채 둡니다. 프롬프트가 돌아오지 않고 로그가 계속 나오는 것은 정상입니다. 편집기의 새 터미널 버튼으로 **터미널 B**를 열고, 같은 폴더인지 확인한 뒤 B에서도 `.venv`를 활성화합니다. B에서 상태 확인·요청을 보내고, 끝나면 A에서 `Ctrl+C`로 내 서버를 중지합니다.

## 같은 이름으로 다시 실행해도 되나요?

| 상황 | 다음 행동 |
|---|---|
| 응답/label/패키지/준비 폴더가 이미 있음 | 먼저 기존 결과를 읽습니다. **새 실행이 필요한 경우만** `candidate-2`, 새 `--output`, 새 `--run` 등을 선택하고 후속 참조도 맞춥니다. |
| File Search 인덱싱 또는 관리형 red-team job이 아직 진행 중 | 해당 장의 **같은 ID/label로 상태 조회·재개** 절차를 사용합니다. 새 자원을 중복 생성하지 않습니다. |
| 설정·원문·코드·모델을 바꿔 비교하고 싶음 | 이전 결과를 보존하고 변경 조건을 기록합니다. 지침만 비교하려면 같은 코드·데이터의 새 baseline/candidate 쌍이 필요합니다. |
| 비용·권한·기능 지원이 막힘 | 생성 반복, 모델 대체, 권한 확대부터 하지 않습니다. 원래 오류와 남은 자원을 기록합니다. |

## 매 장에서 확인할 네 가지

- 내가 만들거나 바꾸는 대상이 무엇인가?
- 지금 사용하는 프로젝트·모델·버전이 맞는가?
- 실제로 확인한 결과는 무엇인가?
- 멈춘다면 무엇을 정리해야 하는가?

명령의 종료, 실제 응답, 품질 통과는 서로 다릅니다. 실패나 미지원 기능은 그대로 기록하고 [문제 해결](troubleshooting.md)의 해당 항목부터 확인합니다.

### 오류가 보이면 다음으로 가도 되나요?

| 실제 상태 | 다음 행동 |
|---|---|
| `ERROR`, traceback, 인증/API 오류, 응답 누락 | 의존하는 다음 명령은 멈추고 해당 장과 문제 해결을 확인합니다. 파일이 생겼어도 성공이 아닙니다. |
| 07의 응답 6개·요청 오류 0개, 일부 업무 검사 실패 | 실패를 읽고 지침 비교는 계속할 수 있습니다. 낮은 점수를 지우려고 같은 수집을 반복하지 않습니다. |
| 관리형 job이 아직 실행 중인데 로컬 대기만 timeout | 해당 장의 같은 ID/label 조회·재개 안내를 사용합니다. 새 job을 제출하지 않습니다. |
| 품질 기준 실패 또는 관리형 판정 불일치 | 분석 결과를 보관하고 최종 인수·holdout은 보류합니다. [15의 중지·정리](15-capstone-cleanup.md#4-먼저-실행-중인-것을-멈추기)는 그대로 수행합니다. |

## 막힌 단계가 있을 때

Search가 준비되지 않으면 06의 Search 의존 단계와 10의 Toolbox/OpenAPI는 멈춥니다. 07의 `local` 검색 평가처럼 Search가 필요 없는 단계는 진행할 수 있습니다. 12에서 로컬 검색을 선택하더라도 Search/IQ 실습 성공으로 기록하지 않습니다. Hosted를 사용할 수 없다면 08/12의 원격 실행은 미실행이며, 15의 SDK 대상과 구분합니다.

| 막힌 지점 | 가능한 다음 행동 |
|---|---|
| 00~01의 기본 Sol 배포·첫 호출 | 다른 모델로 대신하지 않고 Azure 실습을 멈춥니다. 이미 만든 자원은 15에서 확인합니다. |

| 08 원격 Hosted 배포만 미지원 | 로컬 준비가 가능하면 1~3절의 폴더는 연결용으로 쓸 수 있습니다. 09의 Prompt Agent trace, 10의 비-Hosted 도구, 11의 준비된 기능만 진행합니다. |
| 11의 Memory 또는 embedding만 미지원 | Memory는 미실행으로 남깁니다. A2A는 08의 준비 폴더, Routine은 03의 Prompt Agent와 09의 로그가 있으면 각각 진행할 수 있습니다. |
| 12 Optimizer 미지원 또는 후보 0개 | 상태를 기록한 뒤, 선행 조건이 준비된 Hosted `v1`/`v2` 비교로 갑니다. 후보가 없다는 이유로 원문·기준을 바꾸지 않습니다. |
| 13 Hosted 정책 실험 미지원 | 2~4절을 미실행으로 남깁니다. 별도 Prompt Agent·judge·로그 조건을 갖췄다면 5절 관리형 검증은 따로 확인합니다. |
| 14 GitHub 권한 없음 | 15로 갑니다. 14를 건너뛰는 것이 다른 품질 기준을 면제하지는 않습니다. |

다른 프로젝트로 전환할 때는 [00의 보관/새 workspace 절차](00-setup.md#새-프로젝트에서-이전-상태를-인수하지-않기)를 따릅니다. 보관한 이전 CI ID나 배포 이름만으로 새 프로젝트의 권한·자산 소유권을 가정하지 않습니다.

**실패 출력은 보관하고, 미지원·미실행을 완료로 판단하지 않습니다.** [검증 보고서](validation-report.md)의 성공/실패는 참고일 뿐 본인의 실행을 대신하지 않습니다. 중단 시에는 [15의 중지 단계](15-capstone-cleanup.md#4-먼저-실행-중인-것을-멈추기)로 바로 이동합니다. Search Basic은 요청하지 않아도, 보존한 저장소는 compute를 멈춰도 비용이 남을 수 있습니다.

## 파일 전달

개인 설정 없이 실습 자료를 압축하려면:

```bash
python scripts/package_workshop.py
```

ZIP에는 코드·데이터·가이드·테스트가 함께 들어갑니다. `.env`, `.selfstudy`, 실행 결과와 가상 환경은 제외됩니다. 받은 사람은 압축을 풀고 [00](00-setup.md)부터 시작합니다.

이미 ZIP이 있다면 덮어쓰지 않습니다. 새 배포본이 필요할 때만 `--output dist/workshop-new.zip`처럼 아직 없는 파일명을 지정하고 생성된 manifest를 확인합니다.
