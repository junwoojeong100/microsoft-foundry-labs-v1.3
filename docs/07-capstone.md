**55분 · 앱·터미널·워크북 · 목표: 처음 보는 질문으로 확인하고, 무엇을 만들었는지 설명하며, 자원을 정리합니다.**

| 시간 | 할 일 |

## 1. 최종 버전 고정

앱 터미널에서 `Ctrl+C`로 서버를 멈춥니다. 같은 폴더의 터미널에서 선택 상태를 확인합니다.

```bash
python lab.py status
```

워크북에 에이전트 이름, 선택 버전, 프롬프트 해시를 적습니다. 지금부터 holdout 확인이 끝날 때까지 지침·문서·모델·함수를 바꾸지 않습니다.

## 2. 처음 보는 네 문항

```bash
python lab.py evaluate --dataset holdout --label final
```

이제 `outputs/final/review.csv`를 열어 네 응답을 검토합니다. 금액과 날짜, 실제 인용, 도구 입력/반환값, 실행할 수 없는 요구에 대한 응답을 확인합니다.

```bash
python lab.py score --label final
```

**워크숍 품질 목표:** 4/4, critical 실패 0. 하지만 목표에 못 미쳤다고 답변이나 점수를 고치지 않습니다.

| 결과 | 올바른 해석 |
|---|---|
| 응답 수집·검토 완료, 4/4 | 이 작은 최종 세트의 기준을 충족 |
| 응답 수집·검토 완료, 일부 fail | 평가 학습은 수행했지만 품질 목표는 미달 |
| 오류·응답 누락·검토 누락 | 최종 평가 미완료 |

holdout 실패를 보고 지침을 고친 뒤 같은 4문항에서 통과했다면, 그 세트는 더 이상 보지 않은 시험이 아닙니다. 해당 실패는 다음 연습 데이터로 옮기고 **새 최종 문항**을 준비해야 합니다.

**4/4이어도 생산 환경 배포 승인은 아닙니다.** 데이터 권한, 실제 업무 도구, 사용자 인증, 더 넓은 회귀 평가, 장애 대응은 별도입니다. 출력의 `production_approved`도 항상 `false`입니다.

## 3. 짝 시연: 3분 안에 설명하기

필요하면 앱을 다시 엽니다.

```bash
python -m streamlit run app.py --server.address 127.0.0.1 --browser.gatherUsageStats false
```

짝에게 다음 순서로 보여 줍니다. 전체 참가자가 한 명씩 발표하기보다 두 사람씩 동시에 진행합니다.

1. **30초 — 문제:** “반복되는 출장 규정 질문을 줄이되, 근거와 승인 경계를 지키려 합니다.”
2. **90초 — 시연:** 현행 규정 질문, 계산 질문, 자료가 없는 질문을 보여 줍니다. 새 호출 또는 이미 저장한 본인 결과인지 구분합니다.
3. **60초 — 증거:** 실제 파일 인용, 함수 반환값, 평가 전후 결과, trace 중 핵심을 보여 줍니다.

마지막에 역할을 바꿉니다. 청중은 다음을 확인합니다.

- 근거 문서를 열어 확인할 수 있는가?
- 숫자가 실제 함수 반환값과 같은가?
- 못 하는 일을 못 한다고 말하는가?
- 개선했다고 말한 이유에 실제 결과가 있는가?

## 5. 정리: 비용이 남는 것까지 확인

**먼저 앱을 `Ctrl+C`로 멈춥니다.** `outputs/`의 개인 학습 기록을 필요한 범위에서 보관합니다.

### 5-1. 삭제 대상 조회

```bash
python lab.py cleanup
```

이 명령은 **조회만** 합니다. 프로젝트, agent 이름, 생성한 버전, 업로드 파일, 벡터 저장소, 응답 ID가 **내 것인지** 확인합니다.

### 5-2. 확인한 자산만 삭제

아래 이름을 앞 출력의 `agent_name`으로 바꿉니다. **개인 실습 자산 삭제를 결정한 후에만 실행**합니다.

```bash
python lab.py cleanup --confirm "trip-coach-01"
```

스크립트는 이 폴더가 기록한 응답·에이전트 버전·벡터 저장소·업로드 파일만 삭제합니다. 삭제가 거부되면 해당 지점에서 멈추고, 이미 처리한 상태를 보존합니다. 인증·권한을 해결한 뒤 같은 명령으로 남은 것만 정리할 수 있습니다.

다시 `python lab.py cleanup`을 실행해 기록된 목록이 비었는지 확인합니다. 상태 파일은 정리 기록으로 남겨 둡니다. API의 “삭제 성공”은 모든 백업·보관 데이터가 즉시 물리적으로 소거되었다는 뜻은 아닙니다.

### 5-3. 자동 정리 밖의 자산

다음은 스크립트가 만들거나 소유권을 기록한 자산이 아니므로 **포털/담당자가 별도 확인**합니다.

| 자산 | 누가 무엇을 확인하나? |
|---|---|
| 포털에서 만든 평가 run·평가용 데이터 | 본인 생성 항목만 담당자의 보관/삭제 정책에 따라 처리 |
| 포털 Playground의 대화·응답, 별도 저장 버전 | 본인 생성 항목 여부와 보관 정책 확인 |
| 빈 에이전트 항목 | 모든 버전이 정리되었는지 확인 후 담당자 처리 |
| 모델 배포·Foundry 프로젝트·리소스 그룹 | 개인 전용이면 담당자가 삭제, 공유 중이면 삭제 금지 |
| Application Insights·Log Analytics | 로그 보관, 계속 발생하는 비용, 담당자 확인 |
| 별도로 연결한 Storage/Search | 사용 종료·잔여 과금 여부 확인 |

**공유 리소스 그룹을 통째로 삭제하지 않습니다.** 정말 실습 전용이고 다른 사용자가 없다는 것을 확인한 담당자만 그룹 단위 정리를 합니다.

File Search 저장소의 1일 자동 만료는 편의장치입니다. **원본 업로드 파일과 로그까지 모두 정리해 주는 기능은 아닙니다.**
