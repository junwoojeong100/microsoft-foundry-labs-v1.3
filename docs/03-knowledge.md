# Lab 03. 문서에 근거하는 에이전트

**70분 · 파일·터미널·Foundry 포털 · 목표: 진짜 파일 검색과 인용을 사용하는 에이전트를 만듭니다.**

| 시간 | 할 일 |
|---|---|
| 10분 | RAG를 한 그림으로 이해 |
| 5분 | 가상 규정 3개 읽기 |
| 10분 | 파일 검색 에이전트 생성 |
| 15분 | 첫 근거 답변과 포털 확인 |
| 15분 | 과거 규정·없는 정보 질문 |
| 10분 | 원문과 인용 대조 |
| 5분 | 버전과 결과 저장 |

## 1. RAG는 무엇인가요?

**RAG는 답변하기 전에 관련 정보를 찾아 함께 쓰는 방식**입니다. 여기서는 Foundry의 관리형 **File Search**로 구현합니다.

```mermaid
flowchart LR
    Q["서울 숙박비는?"] --> S["File Search"]
    D["업로드한 규정 3개"] --> S
    S --> C["관련 문서 부분"]
    C --> A["모델 + 지침"]
    A --> R["답변 + 파일 인용"]
```

파일 업로드 → 검색 가능한 저장소에 인덱싱 → 질문에 관련된 부분 검색 → 그 근거를 사용한 답변 순서입니다.

**지침에 문서 전체를 붙여 넣는 것은 이번 RAG 실습의 대체가 아닙니다.** 업로드 성공만으로 검색이 성공한 것도 아닙니다. 실제 검색 호출과 인용을 확인합니다.

## 2. 문서 세 개만 읽기

| 파일 | 문서 ID | 반드시 구분할 내용 |
|---|---|---|
| [현행 규정](../data/knowledge/01-travel-current.txt) | TRAVEL-2026 | 2026-07-01부터, 서울 150,000원/박 |
| [과거 규정](../data/knowledge/02-travel-previous.txt) | TRAVEL-2025 | 2026-06-30까지, 전 도시 100,000원/박 |
| [승인·안내 범위](../data/knowledge/03-approval.txt) | APPROVAL-01 | 사전 승인 필요, 해외 규정·연락처 없음 |

과거 문서는 실수로 넣은 파일이 아닙니다. **검색되는 문서와 질문 날짜에 맞는 문서가 항상 같지는 않다**는 점을 배우기 위해 함께 넣었습니다.

## 3. 에이전트를 만들기

터미널에서 한 번 실행합니다. **가상 문서 3개가 내 Foundry 프로젝트로 업로드되고, 파일 검색 비용이 발생할 수 있습니다.**

```bash
python lab.py create --stage rag
```

기대 출력에는 다음이 있습니다.

```text
agent_name: 내 trip-coach 이름
version: 서비스가 반환한 실제 버전
stage: rag
prompt: baseline
indexed_files: 규정 파일 3개
```

코드가 대신 하는 일:

1. 본인 이름의 에이전트인지 확인.
2. Vector Store 생성, 가상 규정 3개 업로드와 인덱싱 완료 확인.
3. [시작 지침](../prompts/baseline.txt)과 File Search를 가진 Prompt Agent 버전 생성.
4. 실제 자원 ID와 버전을 `.lab/state.json`에 저장.

`Vector Store`는 파일의 관련 부분을 검색하기 위한 저장소입니다. 이 입문 경로에서는 청크 크기·임베딩 모델·검색 인덱스를 직접 설계하지 않습니다.

**버전이 1이라고 가정하지 마세요.** 서비스가 반환한 값을 사용합니다. 재실행하면 새 버전이 생길 수 있으므로 출력이 나왔다면 그대로 다음으로 갑니다.

## 4. 첫 질문: 새 규정

```bash
python lab.py ask "2026년 9월 서울 출장 숙박비 상한은 1박 얼마인가요?"
```

**확인할 결과는 세 가지입니다.**

| 확인 | 통과 기준 |
|---|---|
| 금액과 날짜 | 150,000원/박, 2026-07-01 이후 규정 |
| 업무 근거 | TRAVEL-2026 |
| 실제 검색 근거 | 출력 `citations`에 파일 ID가 있으며 해당 파일이 현행 규정임 |

`output_file`의 JSON을 엽니다. `responses[].output`에 `type: "file_search_call"` 항목을 찾아봅니다. `include` 옵션으로 반환된 검색 결과가 있으면 어떤 문서 부분을 사용했는지도 읽습니다.

**맞는 숫자지만 `citations: []`라면 RAG 성공으로 기록하지 않습니다.** 모델이 파일 검색을 생략했거나 인용을 만들지 않은 경우일 수 있습니다. 지침·실제 호출 기록을 확인합니다.

## 5. 포털에서 내 에이전트 확인

1. Foundry의 **Build → Agents** 또는 **Agents** 목록을 엽니다.
2. 방금 출력된 `trip-coach-...` 이름을 선택합니다.
3. 모델, 지침, File Search 도구를 확인합니다. 새 UI에서 도구가 Tools/Knowledge/Toolbox 영역에 표시될 수 있습니다.
4. 저장된 버전이 명령 출력과 같은지 대조합니다.
5. 이 **rag 버전**의 Playground에서 다음 질문을 한 번 전송합니다.

```text
국내 출장은 비용을 쓰기 전에 누구의 승인이 필요한가요?
```

**기대 결과:** 팀장 사전 승인, 상한 초과 시 팀장·재무 담당자의 별도 승인. APPROVAL-01 또는 현행 규정의 해당 내용을 인용합니다.

이 단계에서는 설정을 편집하거나 새 버전을 저장하지 않습니다. 파일 검색은 Foundry가 실행하므로 로컬 계산 서버는 필요 없습니다.

## 6. 과거 규정과 없는 정보

터미널로 돌아와 각각 질문합니다. 각 `ask`는 앞 질문을 이어받지 않는 새 요청입니다.

```bash
python lab.py ask "2026년 6월 부산 출장 숙박비 상한은 1박 얼마였나요?"
python lab.py ask "도쿄 출장 호텔비 상한과 총무팀 이메일을 알려 주세요."
```

| 질문 | 기대 결과 | 실패 예시 |
|---|---|---|
| 2026년 6월 부산 | 과거 TRAVEL-2025, 100,000원/박 | 현재 부산 상한 120,000원으로 답함 |
| 도쿄와 이메일 | 자료 없음, 총무 담당자 확인 | 국내 기타 도시 금액을 적용하거나 이메일을 만듦 |

모든 질문에 대답하는 것이 목표가 아닙니다. **알 수 없는 것을 분명하게 남기는 것도 성공 행동**입니다.

## 7. 인용을 직접 열어 대조하기

응답의 `file_id`를 `python lab.py status`의 `files` 목록과 연결합니다. 해당 [원문 폴더](../data/knowledge/)에서 다음을 확인하세요.

- 정말 그 금액이 있는가?
- 유효 기간이 질문의 날짜를 포함하는가?
- 문서가 말하지 않은 연락처나 승인 상태를 덧붙이지 않았는가?

인용이 있다는 사실은 정확성의 보장이 아닙니다. **잘못된 문서를 그럴듯하게 인용할 수도 있습니다.**

## 막히면

업로드 후 `in_progress`라면 인덱싱 중입니다. 스크립트는 파일당 최대 120초 기다린 뒤 중단하고 상태를 보존합니다. 권한·지원 모델 문제를 [문제 해결](troubleshooting.md)에서 확인하세요. 문서를 지침에 붙여 넣어 성공한 것으로 처리하지 않습니다.

저장소는 마지막 활동 기준 **1일 만료**로 생성됩니다. 다음 날 재개할 때는 만료 상태를 먼저 확인합니다. 원본 업로드 파일은 별도 자원이므로 마지막 정리도 필요합니다.

**핵심 한 문장:** 좋은 RAG는 문서를 많이 넣는 것이 아니라, 질문에 맞는 근거를 찾아 확인할 수 있게 하는 것입니다.
